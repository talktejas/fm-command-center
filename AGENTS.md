## This repo

Standalone extraction of firstmate's command center (originally `bin/command-center.py` etc. in `talktejas/firstmate`). See [README.md](README.md) for running it and [docs/command-center.md](docs/command-center.md) for full behaviour.

- **Never copy or edit firstmate's own scripts.** This repo calls them by path from `--firstmate-root` / `$FM_FIRSTMATE_ROOT` (default `/home/tds/p/firstmate`): `fm-captain-hold.sh`, `fm-send.sh`, `fm-inbox.sh`, `fm-captain-message-sweep.py`, `fm-classify-lib.sh`, `fm-busy-lib.sh`, `fm-secondmate-registry-lib.sh` (sourced by `command-center-scan.sh`), `fm-bearings-snapshot.sh` (wrapped by `command-center-work.sh`). If firstmate's own interface changes, fix the call site here, not the other repo.
- Layout: `command-center.py`, `command-center-scan.sh` and `command-center-work.sh` at the root; the browser page in `web/`; tests in `tests/`, doc in `docs/command-center.md`.
- Reading halves are separate scripts by cadence, not one scan: `command-center-scan.sh` (`/api/items`, 3s poll, change-fingerprinted) reads firstmate's own hold/status records; `command-center-work.sh` (`/api/work`, 15s time-cached, no fingerprint) wraps `fm-bearings-snapshot.sh --json`, which does bounded remote-ledger reads too slow for a 3-second cadence. Never fold the slow one into the fast one's poll path.
- Tests (`tests/command-center.test.sh`, `tests/command-center-state.test.js`) run standalone against a throwaway firstmate home and a real (read-only) firstmate checkout for the scripts above — never against the primary firstmate checkout's live state, and never over a browser. Run with `bash tests/command-center.test.sh` and `node tests/command-center-state.test.js`.
- `test_the_click_returns_before_the_command_finishes` in `tests/command-center.test.sh` is flaky under load (times out waiting on `/api/answer`); confirm against an unmodified checkout before treating a failure there as a regression.
- When pulling a behavioural change from firstmate's copy of these files (e.g. a PR against `talktejas/firstmate`), port only the command-center-specific diff — firstmate's own script signatures may have drifted independently and should be left alone here.
- Every answer sent from **Waiting on you** goes through `deliver_to_inbox` (`command-center.py`) straight to the MAIN home's captain inbox (`fm-inbox.sh note` with `FM_HOME` always the main home) and nowhere else, whatever home the item itself belongs to: no `fm-captain-hold.sh`, no `fm-send.sh`, from this send path - both own a real decision record but both do work a click must not wait on, so firstmate closes the decision itself once it reads the note. An idle second mate keeps no watcher running, so a note left in its own inbox would wait unread - the note is prefixed with the item's own home and id (`[b2b · kk-xyz]`) so main firstmate can forward it on with `fm-send`. Only two outcomes ever reach the page: `sent` or `failed`. Correspondingly, the "Firstmate is not watching …" band only ever names the main home now, since that's the only watch state a send's outcome depends on. See "Where your answer goes" in `docs/command-center.md`.
- Replying or answering never archives or removes anything on its own - beyond moving the one message it settles from Waiting on you to Messages - only an explicit Archive, Hold or Delete click does, all durable server-side in `data/command-center/parked.jsonl` (`/api/park`), the same promise `said.jsonl` makes for what he typed - never browser storage, which was fragile (gone in a private window, invisible from another browser). A message's own Archive stays on its existing record (`captain-messages.jsonl`); everything else - a Waiting-on-you item, and a message's Hold/Delete - goes through `/api/park`. `deleted` is filtered out server-side (`read_messages`, `message_totals`, `/api/items`), never by editing firstmate's own records; the page asks for a second click (`armOrDelete`) since he has no way back. Hold is the captain's own parking and is never sent to firstmate. See "Archive, Hold and Delete" in `docs/command-center.md`.
- `command-center-scan.sh`'s `held_tasks()` only cards a `- [ ] id - title ... (hold: ...)` bullet as a live captain question when it sits under the exact `## Queued` or `## In flight` heading (or before any heading, for minimal fixtures): a narrative section quoting an old decision in the same bullet shape is prose, not a task, however task-shaped its lines look.
- A test that spins up a throwaway `--firstmate-root` (symlinking real `bin/*` in) must also symlink `.tasks.toml` from the real root, or `command-center-scan.sh` reports every backlog as unreadable.
- Archive/Hold buttons live only in a row's own opened pane, never on a list row (removed 2026-09-22). The fixed `.gutter` between the list and the pane (added 2026-09-24, his ask: no scrolling to chase the pane's own buttons) does not duplicate that logic - `gutterArchive`/`gutterHold` just `.click()` whichever `data-archive-*`/`data-hold-*` button the open pane already rendered, or run the bulk actions when a Messages multi-select is active. Delete has no pane button: the gutter's and the selection bar's both call `armOrDelete` over `deleteTargets()` (the selection, else the open message/item).
- Messages support the ordinary file-manager multi-select (`state.selected`, `toggleMessageSelection` in `web/command-center.html`): a plain click opens a row AND sets `selectAnchor` (the row-click handler must keep doing that, or shift-click has no anchor - the 2026-09-28 bug), shift selects anchor..clicked, ctrl/cmd toggles one, the open row seeds a new selection. One Hold/Archive/Delete for the whole selection (`bulkHoldSelected`/`bulkArchiveSelected`/`armOrDelete`); a test runs the served functions in node. The range walks DOM order (`[data-key^="msg/"]` inside `#list`), not any JS-side list, so it always matches what Group by is actually showing on screen.
- **Waiting on you** lists only what firstmate put to HIM (`onHisBoard`/`waitingItems` in `web/command-center-state.js`): captain holds, and a captured message that needs a reply. A worker's own status decision (`needs-decision`/`blocked`, e.g. "CI check failing") is the worker asking firstmate - the scan still reads it and `/api/items` still serves it (reply routing via `waiting_question`/`replyTarget` needs it), but it is never a row or a count on any tab (his ruling 2026-09-28); firstmate escalates one by recording a `--question-key` message. A message needing a reply is one - flagged as a question by `fm-captain-message-sweep.py` (`message.question`) or one whose own words plainly ask him to decide (`looksLikeQuestion` in `web/command-center-state.js`, a deliberately short, tuned-against-the-real-log list of phrases - see the PR that added it for the last-100-message catch rate) - until his LATEST reply to it (`said.jsonl`, newest first) decides something, or the decision it named is closed (`messageNeedsReply`); a reply that only asks firstmate something back (`looksLikeClarifyingReply`: ends `?`, or "what do you mean"/"explain"/"more info"/"which one"/"why") never counts as that decision, so the message stays flagged. **One record, one tab** (his ruling 2026-09-28, a batch Archive in Messages took rows out of Waiting on you): a waiting message is listed ONLY in Waiting on you, never Messages/Info (`inMessagesTab` filters `visibleMessages()` and the badges), and moves to Messages once answered or settled; a Work Captain's Call his board already carries is dropped from Work (`workCalls`). Built in `visible()`/`waitingMessages()` (`web/command-center.html`): the merged rows are tagged `__msg` so `groupOf`/`rowsHtml` can tell a message row from a scanned item without a second isMessage flag per call, and `rowKey` (not the item-only `itemKey`) must be used wherever advance-to-next after an archive/hold walks this merged list, or a message next to the archived row gets a key that opens nothing. A scanned item is NOT symmetric with a message here: answering one, however decisively, never removes it - only Archive/Hold does (it has no Messages-like tab to fall back into the way a message does) - see "Replying or answering never..." below, which is still the rule for items. The badge (`waitingCount`) and the row list (`waitingItems`/`waitingMessageRows`, all in `web/command-center-state.js`) are the same pure functions applied to the same three inputs (scanned items, messages, said) with no dependency on `state.open`/`state.seen`/`state.draft`, so opening a row or typing into it structurally cannot move the count (his report 2026-09-24: "clicked one... now there was only 1").
- The received dot (`web/command-center.html`'s `recvDotHtml`/`sendDotState`) is driven by `said.jsonl`'s `note_id` field - the id `bin/fm-inbox.sh note` prints as `queued <id>` and writes to `state/inbox/<id>.note`, captured however that command's own exit code reads (a nonzero exit there can mean only the *wake* after the write failed, so `note_id` is still captured). `command-center.py`'s `read_said` computes `received` fresh on every non-cached read by checking whether that file has moved to `state/inbox/handled/` (`fm-inbox.sh drain --ack`'s own move) - never cached, because only that filesystem fact says so. `/api/said`'s ETag additionally folds in a stat of every known home's `state/inbox`+`state/inbox/handled` dirs (`Handler._said_fingerprint`) so an ack busts the poll's 304 without first parsing the log to learn which note ids are even outstanding. The client's own `saidDigest` (`web/command-center-state.js`) must include `r.received`, or a poll that only flips that field looks unchanged and the dot never repaints.
- **Nothing leaves Waiting on you except the captain's own Archive/Hold/Delete (or, for a message, a deciding reply, which moves it to Messages)** - his report 2026-09-28, "they just disappeared". Two halves enforce it: (1) scanned items - `command-center-scan.sh` lists only decisions still OPEN, so firstmate closing a hold or writing `resolved` used to delete the row; `remember_waiting` (`command-center.py`, called from `Records._refresh_locked`) keeps every item ever served in `data/command-center/waiting.json` and serves a dropped one on with `closed: true`/`listen: "closed"` until he parks or deletes it, and `waiting_question` skips closed ones so reply routing still treats them as settled (`replyTarget` mirrors that client-side); `closed_answer` attaches what firstmate recorded closing it (`answer`: a hold's last `Captain decision:`/`Reconciliation evidence:` paragraph in the backlog or done-archive, a status line's `resolved [key=K]:` text) so the row reads settled, never as still wanting him; (2) message rows - `loadMessages` (`web/command-center.html`) walks every unarchived `before=` window (`fetchOlder`) before anything renders, because `waitingMessageRows` only sees what the page holds. Never build Waiting on you from a window or from the scan's live list alone.
- `/api/messages`'s window (`MESSAGE_WINDOW`, 200) is a cap on the newest N, not a claim only N exist: archiving one lets the next-oldest slide into view on the very next poll, which reads as "the archived message came back" if nothing says otherwise - the `more`/"Showing X of Y" line under the list exists specifically to rule that out, independent of any archive action.
- Grouped rows (Group by Project/worktree/branch) render bucketed by `groupOf`+`rowsHtml`, NOT by the flat time-sorted order `ordered()`/`orderRows` returns - "next after an archive" must walk the same bucketed order (`displayOrder` in `web/command-center.html`) or the pane jumps to an unrelated group's row instead of staying in the one still open. The bucket ORDER itself (which project comes first) used to be rebuilt every poll from that time-sorted list's own row order, so a new message's fresher timestamp could move its bucket to the top of a 3-second repaint out from under him (his report 2026-09-24: "the project I'm working on goes down"). `groupBuckets` now keeps that order in `state.groupOrder` via `stableGroupOrder` (`web/command-center-state.js`): built once from the chosen key (project name, then worktree/branch) and only ever appended to at the end for a genuinely new group, never re-sorted by time. `#list` is also its own scroll container, so every place that repaints it goes through `paintList`, which keeps his scroll offset across a same-view repaint and only resets it on a real tab/group/filter change.
- `command-center.py`'s `enrich_message*` functions (see the comment above `# --- message context enrichment`) fill a message's project/worktree/branch beyond what firstmate's own sweep/backfill recorded, at read time only, from the live scan, the backlog file (open or closed - a Done row keeps its `repo:`), a task-only-folder's own `data/<id>/launch-brief.md`/`brief.md` (`_task_brief_project`, for a one-off deliverable the backlog never carried at all), `data/projects.md` and (`transcript_task_ids`) the captured row's own `session`/`req` read straight from its Claude conversation transcript. The captain's own order of precedence, enforced in `message_context`: the worker/task the turn was actually handling is checked first and is the only source used once it names anything; only when it names nothing does the message's own words get checked, against every known task id and a per-project alias table (`project_aliases`, `data/projects.md` plus `FIXED_PROJECT_ALIASES`, matched case-insensitively). A message about "the command center" from before `fm-command-center` existed as its own repo reads `firstmate` instead (`COMMAND_CENTER_SPLIT`). Once every tier above finds nothing, `fill_from_nearby_turn` lets a short status ping borrow the project of the nearest EARLIER message in the same session, within 15 minutes, that resolved one. Nothing is ever invented - a row every tier leaves blank reads "Not recorded", same as an unfilled worktree/branch. See `docs/command-center.md`'s Messages section for the exact rule.
- The enrichment above used to re-run in full (including a fresh `transcript_task_ids` read of every named session's transcript file) on every single `/api/messages` poll, for every one of the up to `MESSAGE_WINDOW` rows - fine on a small fixture, ruinous at real scale (measured 108s on the live service, serializing every click behind it). `enrich_messages` now keeps a durable per-message cache at `data/command-center/message-context.json` (`load_message_context_cache`/`save_message_context_cache`) and only recomputes a message that's new to the cache or still "unsettled" (missing a field and less than `CONTEXT_SETTLE_SECS` old - a live scan or the backlog might still fill it in while the task is recent); a message that's fully resolved, or has aged past the settle window unresolved, is served straight from the cache with no I/O. Bump `CONTEXT_SETTLE_SECS` or the cache file's shape only with a matching fixture-scale benchmark (see the PR that added this) confirming the win survives.
- `Work.refresh()` (`/api/work`'s 15s cache) used to run `fm-bearings-snapshot.sh` synchronously in the calling request's own thread whenever the cache went stale, blocking that click for as long as the shell-out took (up to its 90s timeout). Now only the very first refresh (no cached board yet) blocks; every later staleness refresh runs on a background thread while the caller gets the last-known board immediately - a bearings board a few seconds stale beats a click that waits behind a slow remote-ledger read.
- Every tab badge must equal exactly the count of rows that tab lists (his report 2026-09-24: Messages badge 28 over an empty list - held messages counted where they were never shown). `message_totals()` (`command-center.py`) now excludes a held message from both `total` and `archived_total`, the same as `visibleMessages()` (`web/command-center.html`) already excludes it from both tabs' rows - Held is counted, and shown, only under On hold. Messages further splits into **Messages** and **Info**: Messages is the DEFAULT (his report 2026-09-28, a finding filed as Info; an earlier same-day "borderline goes to Info" rule was withdrawn) - Info takes only genuine noise with no result, finding, failure, change or ask anywhere in it, first-match rules in `looksLikeInfoOnly` (`web/command-center-state.js`, documented in `docs/command-center.md`'s Info paragraph), measured against the last 300 real log messages (`data/captain-messages.jsonl` in the firstmate home); re-measure there before touching a phrase list, and never narrow SIGNAL to quiet Messages - burying a result costs him more than noise. Because that split is text-only and exists nowhere server-side, `n-messages`/`n-info` are counted from the loaded window client-side, the same as `n-hold` already was, not from the server's whole-log `total` any more.
- The rail's `Project` dropdown (`renderProjectFilter`/`inProject`, applied inside `visibleMessages()`/`visible()` and the Archived/On hold lists; pass `allProjects` for the pre-filter rows it counts) replaced the home chips 2026-09-28. The `Show` state filter is Waiting-on-you only and hidden elsewhere. A global `[hidden]{display:none !important}` exists because a class's own `display` once beat the `hidden` attribute and left dead controls on screen - don't drop it.
- **My words** was removed 2026-09-28 (his ask) together with the `word` park target and every helper that only fed it; his replies live only in each message's/item's own thread. Don't reintroduce a separate list of his words.
- Pasted/dropped/attached reply images: `POST /api/upload` takes raw bytes (Content-Type is the mime type, not JSON - bigger than the JSON body's own 1MB cap) and saves under `<home>/data/command-center/images/<uuid>.<ext>`, served back at `GET /image/<id>`; a send names the ids it wants (`images: [...]` on `/api/note`/`/api/reply`/`/api/answer`), each checked against a file actually on disk. The delivered note gets `[image: <abs path>]` lines appended (`append_image_markers`) after the typed text - `said.jsonl`'s own `text` stays exactly what was typed, with `images` recorded alongside for thread thumbnails. See "Pasted/dropped images" in `docs/command-center.md`.
- Every URL in free text (a message, a reply, a question, a threaded answer) is a real link: `linkify`/`linked`/`para` (`web/command-center.html`, right after `esc`) is the one place that turns an escaped `http(s)://` run into `<a target="_blank" rel="noopener">`, and every render site that shows free text calls one of the two rather than a bare `esc()`. `tests/command-center.test.sh`'s `test_a_url_becomes_a_real_link_on_every_surface_that_shows_free_text` greps the served page for each known call site, so a call site quietly reverted to a bare `esc()` fails a test rather than shipping silently - keep that test's site list in sync when adding a new surface that shows free text.
- The page has exactly one delegated `document.addEventListener('click', ...)` for every row/button action, and a linked URL (see linkify above) can end up nested inside a row that handler also matches (a row's own `<button>` wraps its text). His report: "why every link i click fucking opens two tabs" - the row-open branch re-rendered `#list` synchronously while the click that also targeted the link underneath was still being handled, which drove the browser into a second navigation. The handler's very first line now bails out (`e.target.closest('a[href]')`) whenever the click actually landed on a real link, before any other branch can act or re-render anything - keep that guard first in source order (a test pins the ordering), and never add a delegated action above it.
- Threading firstmate's answer under his send (his reports "i reced no answr for this yet", 2026-09-28 "no response from u"): `threadRows` (`web/command-center-state.js`) first takes every message whose `answers` field names that send's inbox `note_id` (firstmate writes it with `fm-captain-message.sh --answers <note-id>`, in firstmate's repo), and only for a send with none falls back to the guess `matchAnswer` - same task within the reply's own window, else a plain quote/name of the subject, else nothing; a recorded answer is never in the guess pool. Every conversation pane (a message, an item, a note) interleaves the result. His "Tell firstmate something" notes are their own conversations in Messages (`noteRows`, key `note/<sid>` - a thread, not a return of My words), only when `said.jsonl` marks them `answerable`: don't drop that gate, or every older note reads "awaiting firstmate" forever. See "Threading" and "Recorded answers" in `docs/command-center.md`.
- **Archived** is one merged list (`archivedRows`/`archivedRowHtml` in `web/command-center.html`) of archived messages and items, drawn by the same `messageRow`/`itemRow` + `rowsHtml` every other tab uses and ordered by `archivedEpoch` (the server's `archived_at`, read off the archive/park amendment's own `at`) - never give it per-kind sections or its own markup again; that is how it drifted from the other tabs (his report 2026-09-28).
- A no-mistakes `ask-user findings=… file=…` status line is scanned as the bare "A worker on X stopped and needs a decision from you."; `ask_user_question` (`command-center.py`, applied to every served item after `remember_waiting`, so remembered ones too) replaces it with the findings file's own question and full text, or an explicit "the question itself was not written down" (`question_recorded: false`) - his report 2026-09-28, "need fucking decision on what?". Never serve the bare line as if it were the question.
- **One reply box and one send for every pane** (his report 2026-09-28): `replyBoxHtml`/`wireReplyBox` build an item's and a message's box alike, and the single `#send` button runs `sendReply`, which only picks the endpoint (`/api/answer` vs `/api/reply`). The pane STAYS on the row he answered - the old item path jumped to the next row, so his next Archive hit a row he never opened. Never add a per-tab or per-kind send again; `test_replying_to_one_waiting_row_moves_nothing_else` drives the served Send click handler itself.
- Every `/api/reply` delivery is headed by `reply_body` (`command-center.py`): the message's id, title and task/project/worktree/branch, so firstmate can tell which question a reply answers - never send his bare words from that path.
