## This repo

Standalone extraction of firstmate's command center (originally `bin/command-center.py` etc. in `talktejas/firstmate`). See [README.md](README.md) for running it and [docs/command-center.md](docs/command-center.md) for full behaviour.

- **Never copy or edit firstmate's own scripts.** This repo calls them by path from `--firstmate-root` / `$FM_FIRSTMATE_ROOT` (default `/home/tds/p/firstmate`): `fm-captain-hold.sh`, `fm-send.sh`, `fm-inbox.sh`, `fm-captain-message-sweep.py`, `fm-classify-lib.sh`, `fm-busy-lib.sh`, `fm-secondmate-registry-lib.sh` (sourced by `command-center-scan.sh`), `fm-bearings-snapshot.sh` (wrapped by `command-center-work.sh`). If firstmate's own interface changes, fix the call site here, not the other repo.
- Layout: `command-center.py`, `command-center-scan.sh` and `command-center-work.sh` at the root; the browser page in `web/`; tests in `tests/`, doc in `docs/command-center.md`.
- Reading halves are separate scripts by cadence, not one scan: `command-center-scan.sh` (`/api/items`, 3s poll, change-fingerprinted) reads firstmate's own hold/status records; `command-center-work.sh` (`/api/work`, 15s time-cached, no fingerprint) wraps `fm-bearings-snapshot.sh --json`, which does bounded remote-ledger reads too slow for a 3-second cadence. Never fold the slow one into the fast one's poll path.
- Tests (`tests/command-center.test.sh`, `tests/command-center-state.test.js`) run standalone against a throwaway firstmate home and a real (read-only) firstmate checkout for the scripts above — never against the primary firstmate checkout's live state, and never over a browser. Run with `bash tests/command-center.test.sh` and `node tests/command-center-state.test.js`.
- `test_the_click_returns_before_the_command_finishes` in `tests/command-center.test.sh` is flaky under load (times out waiting on `/api/answer`); confirm against an unmodified checkout before treating a failure there as a regression.
- When pulling a behavioural change from firstmate's copy of these files (e.g. a PR against `talktejas/firstmate`), port only the command-center-specific diff — firstmate's own script signatures may have drifted independently and should be left alone here.
- Every answer sent from **Waiting on you** goes through `deliver_to_inbox` (`command-center.py`) straight to the MAIN home's captain inbox (`fm-inbox.sh note` with `FM_HOME` always the main home) and nowhere else, whatever home the item itself belongs to: no `fm-captain-hold.sh`, no `fm-send.sh`, from this send path - both own a real decision record but both do work a click must not wait on, so firstmate closes the decision itself once it reads the note. An idle second mate keeps no watcher running, so a note left in its own inbox would wait unread - the note is prefixed with the item's own home and id (`[b2b · kk-xyz]`) so main firstmate can forward it on with `fm-send`. Only two outcomes ever reach the page: `sent` or `failed`. Correspondingly, the "Firstmate is not watching …" band only ever names the main home now, since that's the only watch state a send's outcome depends on. See "Where your answer goes" in `docs/command-center.md`.
- Replying or answering never archives or removes anything on its own, in Messages, Waiting on you or My words - only an explicit Archive or Hold click does, and both are durable server-side in `data/command-center/parked.jsonl` (`/api/park`), the same promise `said.jsonl` makes for what he typed - never browser storage, which was fragile (gone in a private window, invisible from another browser). A message's own Archive stays on its existing record (`captain-messages.jsonl`); everything else - a Waiting-on-you item, a My words conversation, and a message's Hold - goes through `/api/park`. Hold is the captain's own parking and is never sent to firstmate. See "Archive and Hold" in `docs/command-center.md`.
- `command-center-scan.sh`'s `held_tasks()` only cards a `- [ ] id - title ... (hold: ...)` bullet as a live captain question when it sits under the exact `## Queued` or `## In flight` heading (or before any heading, for minimal fixtures): a narrative section quoting an old decision in the same bullet shape is prose, not a task, however task-shaped its lines look.
- A test that spins up a throwaway `--firstmate-root` (symlinking real `bin/*` in) must also symlink `.tasks.toml` from the real root, or `command-center-scan.sh` reports every backlog as unreadable.
- Archive/Hold buttons live only in a row's own opened pane, never on a list row (removed 2026-09-22) - a My words conversation with no message or item of its own (a plain note) gets its own small pane (`renderWordPane` in `web/command-center.html`) purely so it still has somewhere for those buttons to live. The fixed `.gutter` between the list and the pane (added 2026-09-24, his ask: no scrolling to chase the pane's own buttons) does not duplicate that logic - `gutterArchive`/`gutterHold` just `.click()` whichever `data-archive-*`/`data-hold-*` button the open pane already rendered, or run the bulk actions when a Messages multi-select is active.
- Messages support shift-click range / ctrl-cmd-click multi-select (`state.selected`, `toggleMessageSelection` in `web/command-center.html`) with one Hold/Archive for the whole selection (`bulkHoldSelected`/`bulkArchiveSelected`) - added 2026-09-24 for a captain archiving many messages one at a time. The range walks DOM order (`[data-key^="msg/"]` inside `#list`), not any JS-side list, so it always matches what Group by is actually showing on screen.
- **Waiting on you** used to be only firstmate's own captain holds; it now also carries a captured message that needs a reply - flagged as a question by `fm-captain-message-sweep.py` (`message.question`) or one whose own words plainly ask him to decide (`looksLikeQuestion` in `web/command-center-state.js`, a deliberately short, tuned-against-the-real-log list of phrases - see the PR that added it for the last-100-message catch rate) - until his LATEST reply to it (`said.jsonl`, newest first) decides something (`messageNeedsReply`); a reply that only asks firstmate something back (`looksLikeClarifyingReply`: ends `?`, or "what do you mean"/"explain"/"more info"/"which one"/"why") never counts as that decision, so the message stays flagged. Built in `visible()`/`waitingMessages()` (`web/command-center.html`): the merged rows are tagged `__msg` so `groupOf`/`rowsHtml` can tell a message row from a scanned item without a second isMessage flag per call, and `rowKey` (not the item-only `itemKey`) must be used wherever advance-to-next after an archive/hold walks this merged list, or a message next to the archived row gets a key that opens nothing. A scanned item is NOT symmetric with a message here: answering one, however decisively, never removes it - only Archive/Hold does (it has no Messages-like tab to fall back into the way a message does) - see "Replying or answering never..." below, which is still the rule for items. The badge (`waitingCount`) and the row list (`waitingItems`/`waitingMessageRows`, all in `web/command-center-state.js`) are the same pure functions applied to the same three inputs (scanned items, messages, said) with no dependency on `state.open`/`state.seen`/`state.draft`, so opening a row or typing into it structurally cannot move the count (his report 2026-09-24: "clicked one... now there was only 1").
- The received dot (`web/command-center.html`'s `recvDotHtml`/`sendDotState`) is driven by `said.jsonl`'s `note_id` field - the id `bin/fm-inbox.sh note` prints as `queued <id>` and writes to `state/inbox/<id>.note`, captured however that command's own exit code reads (a nonzero exit there can mean only the *wake* after the write failed, so `note_id` is still captured). `command-center.py`'s `read_said` computes `received` fresh on every non-cached read by checking whether that file has moved to `state/inbox/handled/` (`fm-inbox.sh drain --ack`'s own move) - never cached, because only that filesystem fact says so. `/api/said`'s ETag additionally folds in a stat of every known home's `state/inbox`+`state/inbox/handled` dirs (`Handler._said_fingerprint`) so an ack busts the poll's 304 without first parsing the log to learn which note ids are even outstanding. The client's own `saidDigest` (`web/command-center-state.js`) must include `r.received`, or a poll that only flips that field looks unchanged and the dot never repaints.
- `/api/messages`'s window (`MESSAGE_WINDOW`, 200) is a cap on the newest N, not a claim only N exist: archiving one lets the next-oldest slide into view on the very next poll, which reads as "the archived message came back" if nothing says otherwise - the `more`/"Showing X of Y" line under the list exists specifically to rule that out, independent of any archive action.
- Grouped rows (Group by Project/worktree/branch) render bucketed by `groupOf`+`rowsHtml`, NOT by the flat time-sorted order `ordered()`/`orderRows` returns - "next after an archive" must walk the same bucketed order (`displayOrder` in `web/command-center.html`) or the pane jumps to an unrelated group's row instead of staying in the one still open. The bucket ORDER itself (which project comes first) used to be rebuilt every poll from that time-sorted list's own row order, so a new message's fresher timestamp could move its bucket to the top of a 3-second repaint out from under him (his report 2026-09-24: "the project I'm working on goes down"). `groupBuckets` now keeps that order in `state.groupOrder` via `stableGroupOrder` (`web/command-center-state.js`): built once from the chosen key (project name, then worktree/branch) and only ever appended to at the end for a genuinely new group, never re-sorted by time. `#list` is also its own scroll container, so every place that repaints it goes through `paintList`, which keeps his scroll offset across a same-view repaint and only resets it on a real tab/group/filter change.
- `command-center.py`'s `enrich_message*` functions (see the comment above `# --- message context enrichment`) fill a message's project/worktree/branch beyond what firstmate's own sweep/backfill recorded, at read time only, from the live scan, the backlog file (open or closed - a Done row keeps its `repo:`), a task-only-folder's own `data/<id>/launch-brief.md`/`brief.md` (`_task_brief_project`, for a one-off deliverable the backlog never carried at all), `data/projects.md` and (`transcript_task_ids`) the captured row's own `session`/`req` read straight from its Claude conversation transcript. The captain's own order of precedence, enforced in `message_context`: the worker/task the turn was actually handling is checked first and is the only source used once it names anything; only when it names nothing does the message's own words get checked, against every known task id and a per-project alias table (`project_aliases`, `data/projects.md` plus `FIXED_PROJECT_ALIASES`, matched case-insensitively). A message about "the command center" from before `fm-command-center` existed as its own repo reads `firstmate` instead (`COMMAND_CENTER_SPLIT`). Once every tier above finds nothing, `fill_from_nearby_turn` lets a short status ping borrow the project of the nearest EARLIER message in the same session, within 15 minutes, that resolved one. Nothing is ever invented - a row every tier leaves blank reads "Not recorded", same as an unfilled worktree/branch. See `docs/command-center.md`'s Messages section for the exact rule.
- The enrichment above used to re-run in full (including a fresh `transcript_task_ids` read of every named session's transcript file) on every single `/api/messages` poll, for every one of the up to `MESSAGE_WINDOW` rows - fine on a small fixture, ruinous at real scale (measured 108s on the live service, serializing every click behind it). `enrich_messages` now keeps a durable per-message cache at `data/command-center/message-context.json` (`load_message_context_cache`/`save_message_context_cache`) and only recomputes a message that's new to the cache or still "unsettled" (missing a field and less than `CONTEXT_SETTLE_SECS` old - a live scan or the backlog might still fill it in while the task is recent); a message that's fully resolved, or has aged past the settle window unresolved, is served straight from the cache with no I/O. Bump `CONTEXT_SETTLE_SECS` or the cache file's shape only with a matching fixture-scale benchmark (see the PR that added this) confirming the win survives.
- `Work.refresh()` (`/api/work`'s 15s cache) used to run `fm-bearings-snapshot.sh` synchronously in the calling request's own thread whenever the cache went stale, blocking that click for as long as the shell-out took (up to its 90s timeout). Now only the very first refresh (no cached board yet) blocks; every later staleness refresh runs on a background thread while the caller gets the last-known board immediately - a bearings board a few seconds stale beats a click that waits behind a slow remote-ledger read.
- Every tab badge must equal exactly the count of rows that tab lists (his report 2026-09-24: Messages badge 28 over an empty list - held messages counted where they were never shown). `message_totals()` (`command-center.py`) now excludes a held message from both `total` and `archived_total`, the same as `visibleMessages()` (`web/command-center.html`) already excludes it from both tabs' rows - Held is counted, and shown, only under On hold. Messages further splits into **Messages** and **Info** (his ask, same PR: pure progress/no-change chatter - "nothing new", "still running", an ack - moves to Info; a real outcome, a landed change, a decision or a problem stays in Messages; `isInfoOnlyMessage`/`looksLikeInfoOnly` in `web/command-center-state.js`, deliberately conservative - never true of a flagged or plainly-asked question, and an unrecognised message defaults to Messages). Because that split is text-only and exists nowhere server-side, `n-messages`/`n-info` are counted from the loaded window client-side, the same as `n-hold` already was, not from the server's whole-log `total` any more.
- My words rows and the opened pane now show what a reply was actually answering, above his own words - `wordOriginal` (`web/command-center-state.js`, pure over the item/message it resolves against) - because a row used to carry only his own text with no way to tell what it replied to (his report 2026-09-24). A genuine standalone note still resolves to `null` and says so plainly; nothing else changed about how a note's own pane works.
